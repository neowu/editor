# Metal rendering review

Reviewed the uncommitted changes against `afd5013f29` on 2026-11-22.

**Keep the demand-driven Metal display link. I would first ship drawable trimming only for windows that stay occluded.** The window already gets an occlusion notification and detaches its link. One delayed visibility check there would let a briefly covered window stay warm and a minimized window give memory back. This removes the need to classify every visible frame, track cursor cadence, or poll the foreground executor. The price is measurable memory retained by a visible window while someone reads. If reducing that footprint is the primary goal, keep a one-shot trim after a drawing burst as well.

## Findings in the change

1. **A blinking cursor keeps the trim watcher alive indefinitely.** After a trim, the next isolated draw sets `last_draw` and its trailing empty update starts a watcher. With a 500 ms blink, the timestamp stays younger than the one-second delay and `last_burst` stays empty. The watcher therefore wakes every second without releasing anything. A watcher already running when scrolling starts also keeps polling throughout the scroll. Each check schedules a high-priority GCD timer, resumes on the main thread, and takes the window lock. The extra work is small per check and continues for as long as that pattern lasts. For a visible-window policy, arm once on the pause after a burst. If drawing resumes, let the next eligible pause rearm it. Accept that a lone frame can leave its small pool warm until occlusion. Simply canceling and creating a timer on every blink would move the scheduling cost to the blink path. [Trim state](../crates/gpui_macos/src/display_link.rs) · [Watcher](../crates/gpui_macos/src/window.rs) · [macOS timer dispatch](../crates/gpui_macos/src/dispatcher.rs)

2. **A synchronous frame request can record a burst without acquiring a drawable.** Both `window_did_change_key_status` and `display_layer` call `drew_synchronously` unconditionally after invoking GPUI. A clean window can skip both draw and present, and a reentrant request can return immediately. That false timestamp can trigger a size change and discard warm path targets after a focus switch. If retaining the heuristic, record synchronous acquisition in the successful detached `nextDrawable` branch. It already sees exactly the event the policy is trying to count. A clean activation after a previous trim should leave the watcher disarmed. [AppKit callbacks](../crates/gpui_macos/src/window.rs) · [GPUI frame decision](../crates/gpui/src/window.rs) · [Drawable acquisition](../crates/gpui_macos/src/metal_renderer.rs)

3. **The one-second threshold makes sparse visible updates pay repeatedly.** An isolated draw followed by a sufficiently long pause qualifies through `last_draw` alone. A status update every few seconds, or short edits separated by reading, can therefore rebuild the drawable pool on each interaction. With a selection, the next draw also allocates path targets during frame encoding. The fixed polling interval can put release almost two seconds after the last draw when a watcher was already pending. The present cost to establish before choosing a visible timeout is the delay to the first displayed frame after idle. [Eligibility check](../crates/gpui_macos/src/display_link.rs) · [Path target allocation](../crates/gpui_macos/src/metal_renderer.rs)

4. **A screenshot can repopulate path textures after the last trim.** A minimized window with a selection can still service `edctl screenshot`. Offscreen capture calls the same `render_frame` that caches the window-sized path targets. It neither consumes a drawable nor arms a watcher. On a hidden window those textures can survive until another draw, resize, or close. This affects automation. If hidden-window memory matters there, have capture drop path targets it created solely for that capture after readback, preserving any cache it found warm. [Capture entry point](../crates/gpui/src/ui_snapshot.rs) · [Shared rendering path](../crates/gpui_macos/src/metal_renderer.rs)

## Memory observed on this Mac

Release build, macOS 27.2.1 arm64, fresh editor data, one 1728 × 1084 point window at 2×. A tightly packed BGRA8 surface at those dimensions costs **28.6 MiB**. I used `edctl` on a scratch text file and sampled the editor process with `footprint`. Values below are its rounded MB figures.

| Same-process samples | IOSurface | Process footprint |
|---|---:|---:|
| Select all, then wait 2.3 s, trial 1 | 88 → 58 | 207 → 174 |
| Repeat, trial 2 | 58 → 58 | 207 → 207 |
| Repeat, trial 3 | 88 → 58 | 207 → 177 |
| Separate launch, select all, minimize, wait 3 s | 58 → 29 | 167 → 114 |
| Same minimized window, capture, wait 6 s | 29 → 29 | 114 → 172 |

After hidden capture, unmapped graphics memory rose from 18 to 47 MB and stayed there at both three and six seconds, consistent with one BGRA8 path resolve texture. Capture also allocates readback and image memory, so the entire process increase cannot be attributed to that texture. These are snapshots of the changed binary. They establish the scale and variability of retained memory. The incremental saving over HEAD, the exact count of drawable objects, and the first-frame latency penalty remain unmeasured.

## Renderer tradeoffs

- **Keep the normal presentation path asynchronous.** GPUI builds or reuses a scene, Metal encodes it into the drawable delivered by the link, and the command buffer presents it. A trailing unused update lets the link discover idleness. Eliminating that callback would require GPUI to explicitly request continued presentation during its one-second high-rate-input window, even with a clean scene. Keep the synchronous `nextDrawable` and `waitUntilScheduled` path scoped to AppKit transactions. The repository documents stalls with per-frame `nextDrawable` on base M-series Macs. [Frame scheduling](../crates/gpui/src/window.rs) · [Platform design](../spec/platform.md)
- **Treat the one-pixel size change as an empirical optimization.** Apple documents `drawableSize` as the texture dimensions and `maximumDrawableCount` as the layer's pool setting (2 or 3). The public API gives no eviction guarantee for a size change. Whole-process IOSurface totals can include other surfaces. Put measured counts and sizes in a performance memo and describe reclamation as best effort in the spec. Switching to `MTKView.releaseDrawables()` would release that view's depth/stencil and MSAA textures. Its contract does not promise eviction of the layer's presentation pool. [Apple drawable size](https://developer.apple.com/documentation/quartzcore/cametallayer/drawablesize) · [Pool count](https://developer.apple.com/documentation/quartzcore/cametallayer/maximumdrawablecount) · [MetalKit release semantics](https://developer.apple.com/documentation/metalkit/mtkview/releasedrawables%28%29)
- **Keep path memory separate in the accounting.** Each path batch interrupts the main pass, rasterizes into a window-sized target, then composites the affected bounds. On Apple GPUs the 4× MSAA attachment is memoryless. The private resolve texture is the significant persistent allocation. On the Intel fallback the MSAA attachment also has private backing. Trimming both on occlusion is reasonable. For an active selection the next blink can need them again. A smaller change for path-heavy CPU workloads would be to write expanded vertices directly into the existing instance writer, avoiding the temporary vector and copy per batch. The repository's earlier typing profile put most CPU time in GPUI frame building, so I would leave the path passes alone unless a path-heavy trace changes that ranking. [Path encoding and buffer writer](../crates/gpui_macos/src/metal_renderer.rs) · [Prior measurements](research/performance.md)

## What would change the decision

All 16 `gpui_macos` library tests passed. The new renderer test checks restored dimensions and dropped texture handles on a standalone layer. The state tests check eligibility using supplied timestamps. Neither exercises desktop presentation timing or counts actual pool evictions.

Compare HEAD, the current change, and occlusion-only trimming at the same drawable size. Repeat a short scroll followed by an idle pause and the next keystroke, with and without a selection, then repeat across minimize/restore. Record settled IOSurface bytes, trim callbacks per minute of cursor blink, and p50/p95 time from that first input to the drawable's actual presentation. Include missed refreshes, especially at 120 Hz where a frame interval is 8.3 ms. `edctl perf` measures CPU time inside the platform draw call and misses the interval before the link supplies its drawable. A presented handler or Metal System Trace covers that interval. I would keep visible burst trimming if it consistently saves a window-sized surface and the first input still meets the same refresh deadline as the warm baseline.
